| [open-gsd/gsd-core](https://github.com/open-gsd/gsd-core), v1.20.0 (3 Nov 2026), MIT | "A light-weight meta-prompting, context engineering, and spec-driven development system"; the continuation of Get Shit Done (the archived `glittercowboy/get-shit-done` points to it); 72 slash commands; a loop of discuss, plan, execute, verify, ship per phase; TDD (red, green, refactor) is an opt-in execution mode (`workflow.tdd_mode`, off by default), while the default checks map automated test coverage to the requirements "before any code is written" and verify each phase against what was planned |

Slide 37 states the common ground at the strength all four share: a check is set before the code. Only superpowers and Pocock's skills make a failing test the rule; the Karpathy file asks for tests first as advice, and GSD Core plans test coverage first and leaves full TDD as an option. Pocock's README contrasts its small skills with systems such as GSD that "try to help by owning the process"; the speaker notes mention this as a difference, not a verdict.

## Methods and evidence

- K. Beck, *Test-Driven Development: By Example*, Addison-Wesley, 2002: the red, green, refactor loop.
- The other books on slide 25, with the idea taken from each: A. Hunt, D. Thomas, *The Pragmatic Programmer*, Addison-Wesley, 1999 (20th anniversary edition by D. Thomas and A. Hunt, 2019): "no one knows exactly what they want", tracer bullets; K. Beck, *Extreme Programming Explained*, Addison-Wesley, 1999 (2nd edition with C. Andres, 2004): user stories, which the `to-spec` template asks for, and investing in the design every day; M. Fowler, *Refactoring*, Addison-Wesley, 1999 (2nd edition 2018), chapter 3: code smells; E. Evans, *Domain-Driven Design*, Addison-Wesley, 2003: a ubiquitous language; J. Ousterhout, *A Philosophy of Software Design*, Yaknyam Press, 2018 (2nd edition 2021): deep modules, design it twice.
- N. S. Mathews, M. Nagappan, [Test-Driven Development for Code Generation](https://arxiv.org/abs/2402.13521), ASE '24 (doi 10.1145/3691620.3695527): giving the model tests together with the problem statement solved more problems on MBPP and HumanEval with GPT-4 and Llama 3. Function-level benchmarks, not research code.
- M. Nygard, [Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions), 15 Nov 2011: ADR sections, numbering, superseded records.
- S. Kapoor, A. Narayanan, Leakage and the reproducibility crisis in machine-learning-based science, Patterns 4(9), 100804 (2023): background on leakage.

## Data and images

All micrographs come from the open HCCI SEM dataset (high-chromium cast iron, one specimen per material state). The README of that dataset, October 2026, is the source for the dataset facts on the slides: one overview area per specimen and etchant, with a detail area inside it sampled 5× more finely; 60 to 66 micrographs per area on one pixel grid, sharing one mask; the position of each detail area in its overview (section 7); and the phase classes that occur in one material state only (section 4). `presentation/tools/prepare_hcci_images.py` crops or downscales the micrographs and copies the mask; `presentation/assets/hcci/provenance.csv` lists each output with its source file, dataset ID and acquisition metadata. The dataset credits are listed on slide A11.
